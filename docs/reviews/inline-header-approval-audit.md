# XD inline-header approval audit

## Judgment

The graphics/vector bodies and camera-object ownership are credible. The **specific partition into declaration, graphics-inline, vector-inline and singleton-copy headers, with late includes around a peephole reset, was insufficiently justified for final source-quality acceptance**. The record establishes why this arrangement reproduces emission order and instructions; it does not supply a reasonable original-era developer or build rationale for choosing it. Its approval as realistic recovered source should be reassessed.

`GSgfxInline.h` is not inherently an unrealistic filename. Separating C++ inline implementations can be ordinary. The concern is the coordinated partition and inclusion choreography, not the word `Inline` or the natural three-assignment copy body. The supplied SDK itself contains real `static inline` FIFO implementations in [GXVert.h:48](D:/OSS/decomp-robot/backend/projects/GXXE01/decomp-workspace/dtk-template/src/ext/dolphin_sdk/include/dolphin/gx/GXVert.h:48).

## Why reviewers accepted it

Final reviewer A, `3a99ba5a-d3dd-4022-96d3-4f118ea8876e`, tested more than isolated instructions. Moving the copy body into the ordinary top declaration header retained every function's instruction match but moved `GSvecCopy` from offset `0xC14` to `0x89C`, producing 803 raw text differences. Removing the reset changed `GXParam1u8`; removing suppression changed camera/graphics bodies. The complete submitted 3,120-byte camera text and freshly linked DOL matched. These establish a working explanation of code generation. They do not uniquely identify the historical source arrangement. The review experiment explicitly acknowledged that limitation. See [A's transcript](D:/OSS/decomp-robot/.tmp/xd-agent-inspection-20261009/floor-final-review-A-messages.json), sequence 40, `call_6dcce10ab4d24965b53f88c5066b1270`.

A nevertheless classified the split headers as subsystem ownership and concluded: “Exact historical header filenames and indistinguishable C-linkage scalar types remain non-material historical uncertainty, not evidence of incorrect architecture.” Final reviewer B, `fd45235f-8582-4d20-8fac-64a6fdbc80e2`, approved after 28 compiler configurations and map checks, finding ordinary bodies and credible ownership. B also found camera `-inline on -opt nodeadstore` matched, so early reduced experiments did not uniquely establish `-inline off`. Both final acceptance reasons are in [the review history](D:/OSS/decomp-robot/.tmp/xd-agent-inspection-20261009/floor-review-history.json). My inference: reviewers extended sound object-ownership evidence to a finer header architecture that it did not establish.

The map supports the emitted object and surviving function names. It does not establish these header filenames, partitioning, include order or pragmas. Absence of `Inline` in a link map does not contradict inline source: maps describe emitted symbols and objects, not every contributing header or source keyword. The concern remains independently supported by the recorded emission-driven construction process.

Literal original-source proof and exhaustive elimination of alternatives are unnecessary. Reviewers should distinguish “this layout matches” from “this layout is realistic developer source” and reject unsupported matching scaffolding rather than accept it for later cleanup. This complements existing architecture requirements at shared-standard lines 18 to 22 without making mere uncertainty a blocking defect.
